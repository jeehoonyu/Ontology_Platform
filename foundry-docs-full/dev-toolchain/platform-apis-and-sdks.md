## What it is

The Foundry **Platform APIs** are a versioned, developer-friendly REST interface (v1 and v2) that expose virtually every Foundry resource — datasets, ontology objects, orchestration schedules, connectivity connections, media sets, and more — over HTTP using JSON. The **Platform SDKs** (Python and TypeScript, with Java and OpenAPI also available) are generated client libraries that wrap those REST endpoints. The **Ontology SDK (OSDK)** is a specialized, code-generated layer on top that produces strongly-typed language bindings derived from *your specific ontology*, enabling frontend and backend apps to read objects, fire actions, and call functions with minimal boilerplate.

## How it works

### 1. Register an application in Developer Console

All programmatic access starts in <span style="color:#8ABBFF">**Developer Console**</span>. A developer creates a **Custom Application**, which bundles an OAuth authorization client, a scoped OSDK package, auto-generated SDK docs, permissions, and optional web hosting under one resource.

### 2. Configure OAuth 2.0 credentials

Foundry uses **OAuth 2.0** exclusively for production authentication. Two grant types are supported:

- **Authorization Code Grant** — for apps that act *on behalf of a logged-in user*. The user is redirected to Foundry to authenticate; the app receives a short-lived access token.
- **Client Credentials Grant** — for headless service-account workflows. The app authenticates directly with a client ID and secret; no user interaction is required.

Both grant types issue short-lived access tokens. The actual permissions granted are the *intersection* of the requested OAuth scopes (e.g. `api:ontologies-read`, `api:ontologies-write`) and the user's or service account's existing Foundry permissions. Developers can further narrow the scope from the **Ontology SDK Panel** inside Developer Console.

> For local development only, a bearer token can be generated at `Account → Settings → Tokens`. These tokens inherit the generating user's full permissions and must never be used in production or committed to source control.

### 3. Select ontology resources and generate the OSDK

Inside the application's **SDK tab**, the developer selects the subset of object types, action types, and query functions the application needs. Foundry code-generates a versioned SDK package containing:

- **Typed object interfaces** with property names, descriptions, and link/relationship traversal methods.
- **Action invokers** that call the corresponding Ontology action types and write back to Foundry.
- **Query callers** that invoke Foundry Functions on the server side.
- **Integrated API docs** that appear directly in the Developer Console UI and in the IDE (via JSDoc/docstrings).

The package is distributed as a standard artifact: an **npm** package (TypeScript/JavaScript), a **pip/conda** package (Python), or a **Maven** artifact (Java). Any language can also use the raw **OpenAPI specification** generated by the same process.

### 4. Install, authenticate, and make calls

A consuming application installs the SDK package and constructs a client:

**Python**
```python
import foundry_sdk
auth = foundry_sdk.UserTokenAuth(token=os.environ["BEARER_TOKEN"])
client = foundry_sdk.FoundryClient(auth=auth, hostname="<your-hostname>")
```

**cURL (raw REST)**
```bash
curl -H "Authorization: Bearer $FOUNDRY_TOKEN" \
     -H "Content-type: application/json" \
     "https://<hostname>/api/v2/ontologies/company/objects/employee"
```

Every request goes over HTTPS. The hostname is the same host visible in the browser URL bar for your Foundry environment.

### 5. Resource categories covered

The Platform API surface spans eight resource groups, each with its own URL namespace under `/api/v2/`:

| Group | Key operations |
|---|---|
| **Ontologies** | Read/search objects, invoke actions, call queries, manage attachments |
| **Datasets** | Create/read files, manage branches and transactions |
| **Orchestration** | Trigger builds, manage schedules and jobs |
| **Filesystem** | Manage spaces, projects, and folders |
| **Admin** | Users, groups, organizations, auth providers |
| **Connectivity** | Connections, imports, virtual tables |
| **Streams** | Streaming datasets and records |
| **Models** | Live deployments, model versions |

### 6. Advanced: Custom Endpoints and Palantir MCP

Beyond standard API calls, developers can deploy **Custom Endpoints** — user-defined API routes backed by Ontology actions and Functions — enabling external systems to call bespoke logic hosted in Foundry. The platform also implements the **Model Context Protocol (MCP)**, allowing AI IDEs and autonomous agents to interact with Foundry APIs to build or modify applications programmatically.

## Worked example

**Scenario:** A data science team wants a Python script that reads `FlightDelay` objects from the Ontology and triggers a `RerouteAction` when delay exceeds a threshold.

1. **In Developer Console**, create a new Custom Application named `flight-ops-bot`.
2. On the **OAuth & Restrictions** tab, choose **Client Credentials** grant (no user interaction). Copy the client ID and secret into environment variables.
3. On the **SDK Documentation** tab, click **Add Resource** and select the `FlightDelay` object type and the `RerouteAction` action type. Click **Generate SDK**. The console displays an `pip install flight-ops-bot-sdk==1.0.0` command.
4. In the Python project, install the package and write:
   ```python
   from flight_ops_bot_sdk import FoundryClient, ClientCredentialsAuth
   client = FoundryClient(
       auth=ClientCredentialsAuth(client_id=..., client_secret=...),
       hostname="company.palantirfoundry.com"
   )
   for flight in client.ontology.FlightDelay.where(delay_minutes__gt=30):
       client.ontology.actions.RerouteAction(flight_id=flight.id, reason="delay")
   ```
5. The SDK handles token acquisition, refresh, and scoping automatically. The action writes back to the Ontology and triggers any downstream Foundry pipelines linked to `RerouteAction`.
