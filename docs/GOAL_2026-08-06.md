# Goal — Bounded on the Path the Product Actually Takes

Stated 2026-08-06 on `codex/builder-ux-production`. This goal does not restate the
outcome, scope, or severity gate of [`GOAL_2026-08-03.md`](GOAL_2026-08-03.md); those
govern it. It adds a third invariant to [`GOAL_STANDING.md`](GOAL_STANDING.md) and a
program of work that discharges it.

## Why this goal exists

The Tier B ontology-scale gate passes at 10,000,000 objects and 50,000,000 links, with
lookup p95 8.916 ms, range p95 12.248 ms and two-hop p95 14.153 ms. The evidence file is
honest and current at head `0038`.

It measures a query shape the product never issues.

The gate reads an object set with no residual filter. Every surface a user actually
touches sends a filter, a facet, or a spatial predicate, and each of those takes a
different code path — one that loads the entire object type into memory first.

Measured 2026-08-06 by `oms/measure_read_path_bounds.py`, worst of three, on SQLite.
Growth is normalized to a 10x cardinality step, so a bounded read reads x1 and a read
that materializes the type reads x10:

| Query shape | 25,000 | 100,000 | 400,000 | per 10x |
| --- | ---: | ---: | ---: | ---: |
| **Latency** | | | | |
| Typed read, no filter — *the shape the gate measures* | 2.7 ms | 1.4 ms | **1.3 ms** | **x0.5** |
| Typed read, one equality filter — the Object Explorer | 110.0 ms | 672.6 ms | **2,235.1 ms** | **x12.2** |
| Facet aggregation — the Explorer's left rail | 314.1 ms | 1,993.4 ms | **6,390.3 ms** | **x12.2** |
| Spatial radius query — the Operational Map | 482.5 ms | 1,657.6 ms | **7,119.4 ms** | **x9.3** |
| **Peak heap, one request** | | | | |
| Typed read, no filter | 0.1 MB | 0.1 MB | **0.1 MB** | **x1.0** |
| Typed read, one equality filter | 19.1 MB | 75.6 MB | **302.5 MB** | **x9.9** |
| Facet aggregation | 57.3 MB | 228.0 MB | **912.8 MB** | **x10.0** |
| Spatial radius query | 57.3 MB | 228.0 MB | **912.8 MB** | **x10.0** |

The heap column is the finding. Three of the four shapes grow x9.9 to x10.0 per 10x
objects — memory proportional to the object type, exactly and not approximately — while
the measured shape is flat at x1.0.

Extrapolating from here put one Object Explorer filter click at roughly 7.6 GB and one map
render at roughly 22.8 GB at the 10,000,000 objects the gate certifies. Both were later
measured directly, on Postgres, and the filtered read came in at **21.9 GB** — nearly
three times the projection, because the production dialect had no pushdown at all where
SQLite narrowed the candidate set first. The measured table is below; this one is kept
because it is what prompted the work and because the projection it supported was wrong in
a direction worth remembering.

This is not a platform that is slow at scale. It is a platform that dies at the scale its
own evidence file certifies, on every path except the one that was measured.

Two details make the reading worse rather than better:

- The measurement ran on **SQLite, the favorable dialect**. `_pushdown_equalities` returns
  `[]` for every dialect except SQLite, by design and with a comment saying Postgres
  pushdown is "a later hardening step". Production is Postgres, where the filtered read
  has no pre-filter at all and materializes the whole object type rather than the
  matching third.
- `_logic_object_rows` calls `.all()` and applies its `limit` argument to the resulting
  Python list. The limit never reaches SQL. So a call site asking for **five** rows loads
  the entire object type, and all twenty-one call sites are unbounded regardless of what
  they pass.

## The finding this generalizes to

The gate is not wrong and its evidence is not stale. Neither standing invariant fires:
the proof is current at the head, and the extensibility ratchets are green. The claim is
false anyway, because **the measurement entered the system somewhere the product does
not**.

The same shape appears a second time, independently, in this session's other reading. The
extensibility audit reports `semantic types the UI can render 13 of 13`. All thirteen
hits come from one file — `frontend/src/utils/semanticRender.tsx`, the renderer itself.
Exactly one workspace of twenty-two imports it. The audit would still read 13 of 13 if no
component consumed it at all, because it measures the renderer's vocabulary and not its
reach. The Operational Map — the surface where a `geopoint` and a `geoshape` most
obviously belong — passes raw properties to `KeyValueGrid` with no specs, so a polygon
still reaches the user as GeoJSON text.

Two instruments, both honest about what they measured, both certifying a product property
that does not hold, for the same reason: **a component measured in isolation says nothing
about the composition that ships.**

## The invariant

Added to [`GOAL_STANDING.md`](GOAL_STANDING.md) as the third:

> **A measurement is evidence only for the path it traverses.** Every gate names the entry
> point it enters through and the request shape it issues. A gate that enters below the
> product's own entry point states, in its evidence file, what it therefore does not
> cover.

This is not a restatement of "no claim outlives its proof". That invariant asks whether
the proof is current. This one asks whether the proof is *about the product*. A gate can
be re-run every commit, at the current head, forever, and still certify nothing a user
will experience.

## Ending conditions

Numeric, measured on the reference profile at three cardinalities — 100k, 1M and 10M —
and on both dialects. Every condition carries an evidence file in the envelope defined by
[`TIER_B_MEASUREMENT_CONTRACT.md`](TIER_B_MEASUREMENT_CONTRACT.md).

### B1 — Reads are bounded by the page, not by the object type

For each of four shapes — unfiltered read, filtered read, facet aggregation, spatial
predicate — across each 10x cardinality step:

- peak heap per request grows **≤ 1.5x**, and
- p95 latency grows **≤ 2x**, and
- peak heap per request stays **≤ 64 MB** at every cardinality.

The growth bounds are the real gate; they are host- and dialect-independent, and they are
what "bounded" means. The absolute ceiling is a backstop against satisfying the growth
bound at a uniformly terrible constant.

The reading that opened this condition, from `oms/measure_read_path_bounds.py`, which
implements it and exits non-zero: heap grew **x10.0** per 10x against a x1.5 bound, latency
**x12.2** against a x2.0 bound, and peak heap reached **912.8 MB** against 64 MB — at
400,000 objects, 4% of the certified scale.

**Memory satisfies this condition everywhere.** At 10M on Postgres no shape exceeds
6.9 MB, against a ceiling of 64 MB and a starting reading of 21,940.6 MB.

**Latency satisfies it for every shape a user waits on**, once B3 and B4 landed: the
unfiltered read 12.6 ms, the filtered read 6.6 ms, the facet read 1.4 ms, the map viewport
78.6 ms. What remains unbounded is the facet's *exact* aggregate at 56,487.9 ms, which is
now paid by a refresh rather than by a request, and the radius query at 33,090.3 ms, whose
cost is 570,000 co-located matches in a fixture with a thousand distinct positions rather
than anything the index does.

B1 is **met for the read path**. The honest residue is that the radius shape has never
been measured against a realistic spatial distribution, so its number describes the
fixture and not the system.

### B2 — No route can materialize an object set — **met**

`oms/audit_query_bounds.py` reports **0** object-set materializations whose size is a
function of object-type cardinality, reachable from an HTTP route, down from 24. Ratcheted:
the count may fall and never rise.

The audit derives each primitive's status from its own source every run rather than
carrying a hand-maintained verdict, so a primitive that stops streaming re-fails the build
without anyone remembering to update a constant. The chaos gate's hand-maintained zero is
why that matters.

Baseline **24**, across 9 modules — 21 via `_logic_object_rows`, 3 via
`_query_object_rows`. The affected modules were not a corner of the system:
`object_explorer_ops` (the primary object UI), `gis_ops` (the map), `mcp_tools` (the MCP
surface other programs consume), `quiver_runtime` (analytics), `slate_runtime` and
`workshop_runtime` (the surfaces for building applications on the ontology),
`notepad_ops`, `aip_agents`, `runtime`.

### B3 — Exact totals do not cost a scan — **met**

`0040_object_facet_counts` stores each facet's buckets, refreshed out of band, read with
its `computed_at` beside it. At ten million objects, the same corpus:

| | latency |
| --- | ---: |
| Exact aggregate | 51,521.8 ms |
| Refresh, paid out of band | 53,627.8 ms |
| **Rollup read** | **1.4 ms, 0.8 ms, 1.1 ms** |

Counts identical, total 10,000,000. A facet read no longer costs a scan, which is what
this condition asked for.

It took three wrong answers to get here, each discarded on measurement rather than
argument:

- **An expression index over the grouped expressions.** Built; the planner declined it,
  and forced with `enable_seqscan = off` it was *slower* — 2,589 ms against 1,039 ms at
  one million. The profile's `indexed` flag would have driven a feature that does not
  work.
- **Stale planner statistics.** A real defect in the harness worth 596x on another shape,
  and worth nothing here: with `ANALYZE` current the facet at ten million measured
  56,487.9 ms against 49,011.5 ms without. Not the cause.
- **Blaming jsonb extraction.** The decomposition read 92% on a hot page cache and 62% on
  a cold one — 1,807 ms versus 24,824.9 ms for the *identical* control query. Both
  components are O(n), so the split never mattered.

What survived all three is that a facet over ten million rows is a full aggregate however
it is written. The only way to answer in milliseconds is not to aggregate at read time.

The rollup is refresh-based rather than incrementally maintained, deliberately. Keeping
counts exact on every write means tracking each property's previous value on update, and
a defect there corrupts the numbers silently — the failure mode this entire goal exists
to catch. A refresh is a scan whose cost is visible and whose staleness is declared:
`source` and `computed_at` are in every response, and the rollup refuses to serve a
filtered aggregate, an expired one, or one where metrics were requested.

### B3, as originally written — pushed down only

`aggregate_object_set` now issues a `GROUP BY` instead of carrying every row into Python,
for the count-only case on a single top-level property with no residual predicate. At 10M
that took the facet aggregation from **138,681.6 ms to 40,957.8 ms** and its memory from
6.8 MB to 1.4 MB.

The pushdown is deliberately narrow. Each excluded case — metrics, a dotted or reserved
field, a residual predicate — is somewhere SQL and Python's `str()` could disagree, and a
faster aggregate that returns different numbers is not an improvement. Group keys are
rebuilt to Python's spelling (`True`, not `true`; `"null"` for both a JSON null and a
missing key), and an object- or array-valued key aborts the pushdown rather than inventing
a rendering Python would not produce.

41 seconds is not interactive, and the reason is now measured rather than guessed. The
same scan with trivial per-row work costs **1,807 ms**; with the jsonb extraction it costs
**23,981 ms**. **Roughly 92% of the time is jsonb traversal, not I/O**, so the remedy is
not a faster scan but not traversing: an expression index storing the extracted value
turns this into an index-only scan.

**Correction, 2026-08-07.** This paragraph originally said the profile's `indexed` flag was
"written today and read by nothing", and proposed honouring it as the fix. Both halves
were wrong. `ontology_runtime_v1._plan_index_definition` reads the flag and creates a
btree expression index per indexed property — the `ix_oi_property_*` indexes, two of which
occupy 1,010 MB on the benchmark corpus. The mechanism proposed here already exists, and
it does not serve a full `GROUP BY`, which is what the measurement showed independently
when a hand-built index of the same shape was declined by the planner.

The claim was made from reading the ontology editor and the profile schema without
checking who consumed the column. It is the same mistake as the `interfaces configured`
reading recorded in [`GOAL_STANDING.md`](GOAL_STANDING.md): a capability declared absent
on the strength of not having looked for its consumer.

### B3, as originally written

No route returns an exact total that requires materializing the set. Each total is either
a SQL `count(*)`, or a capped count declared as capped in the response.

This condition exists because it is the *cause* of the other twenty-four. The reason call
sites pass `limit=10 ** 9` is that `_logic_object_rows` returns `len(matched)` alongside
the rows, and an exact total over a filtered set is only obtainable by filtering
everything. The API contract forces the scan; fixing the call sites without fixing the
contract will reintroduce it.

### B4 — Spatial predicates are evaluated in the database — **met**

`0039_object_geo_bounds` materializes each object's extent into four columns, maintained by
a mapper-level listener on every ORM write and backfilled for existing rows. A GiST index
over `box(point(geo_min_lon, geo_min_lat), point(geo_max_lon, geo_max_lat))` — Postgres's
built-in geometric type, no PostGIS — answers the intersection.

**Measured at 10,000,000 objects: a map viewport returns in 70.6 ms against the 250 ms
gate**, holding 5.3 MB, and the plan is a bitmap index scan reading 10,100 index entries
for 10,000 matches rather than a sequential scan of ten million rows. The reading was
taken while the test suite was competing for the same CPUs, so it is conservative.

Three qualifications, none of which change the verdict but all of which bound it:

- It is **one observation, not a p95**. The threshold was written as a p95 and this is a
  single timing; the margin is 3.5x, which is why it is reported as met rather than
  re-run for a distribution.
- The fixture still places ten million objects on **1,000 positions**, so the viewport
  covers one position and matches 10,000 objects. That is a dense but legitimate viewport;
  what the fixture cannot exercise is a *variety* of spatial distributions.
- The **radius** shape is still 39,514.7 ms, because against this fixture a 400 m radius
  matches 570,000 objects and the cost is scoring and ranking that match set, not finding
  it. That is the fixture, not the index.

### B4, as originally written — pre-filter only

A bounding-box pre-filter now runs in SQL on both dialects before any geometry reaches
Python, derived from an explicit bbox, a polygon's extent, or the square enclosing a
radius. At 10M it took the spatial query from **203,135.3 ms to 44,802.8 ms**, more than
reversing the 19% regression that streaming had introduced.

It recognises point-shaped geometry only, in the two forms actually stored: a GeoJSON
Point under the configured field, and bare `longitude`/`latitude` scalars. Everything else
yields NULL and passes through unjudged, which is what keeps the pre-filter a superset —
a Polygon's `coordinates[0]` is an array, and in Postgres casting it to a float aborts the
statement rather than returning null, so the cast happens only where the value is known to
be a number. Near the poles and across the antimeridian the box is declined rather than
approximated, because the Python pass is correct without it.

**The 250 ms gate is not met, and the reason is measured.** For a selective viewport at
10M the pre-filtered query takes **11,006 ms** as a parallel sequential scan. An
expression index over the same predicate is built and then *not used*, because of the
`OR unjudgeable` branch: remove that branch and the identical query becomes an index scan
at **674 ms** — a 16-fold difference attributable to one disjunct.

That disjunct cannot simply be dropped; it is what makes the filter safe for non-point
geometry. Closing B4 therefore means removing the *need* for it, by materializing each
object's bounding box on write. Every row with geometry then has a comparable extent, the
filter becomes a plain conjunction over real columns, and rows without geometry are
correctly excluded rather than waved through — the same rows the Python pass skips anyway.
That is a write-path change with a backfill, and it is specified here rather than
half-built, with the 674 ms measurement as the reason to believe it pays.

The fixture also cannot demonstrate this gate: it places ten million objects on **1,000
distinct positions**, so a 400 m radius legitimately matches 570,000 of them. A real
viewport returns thousands. Any future run against this gate needs a corpus with realistic
spatial spread, and that is a defect in the measurement apparatus, recorded rather than
worked around.

### B4, as originally written

This is also the precondition for the GIS work already on the roadmap. A spatial platform
whose spatial query is a Python loop over every row does not acquire scale by adding
layers on top.

### B5 — Predicate pushdown is not dialect-specific

Equality, comparison and existence predicates push into SQL on Postgres as well as
SQLite, with a measured Postgres reading for every shape in B1. Where a predicate cannot
push down, the route declares the residual and bounds the candidate set rather than
materializing it.

### B6 — Semantic rendering reaches every surface that shows object properties — **met**

New ratchet in `oms/audit_extensibility.py`: **data surfaces receiving declared specs, of
surfaces rendering ontology object properties.** `DataTable` gains a specs parameter;
`KeyValueGrid` call sites that render object properties pass them; the Map inspector
included.

The verified baseline is the numerator: **one** surface receives specs, `ObjectExplorer`,
and it is the only one of twenty-two workspace modules that imports the renderer at all.
The denominator is not yet established — most of those twenty-two render operational or

stated here as unknown rather than guessed.

The existing `renderable_base_types` reading stays but is relabelled as vocabulary, not
reach, so that 13 of 13 stops reading as a coverage claim.

### B7 — The scale gate enters through the product's door

The Tier B ontology-scale harness issues its reads through `/api/v1`, using the request
shapes the Object Explorer and the Operational Map issue — including at least one filter,
one facet aggregation and one spatial predicate — and its evidence file names the entry

Until B7 lands, the Tier B ontology-scale row carries an explicit note that it certifies

## Measured at reference scale, and repaired

Condition B1's first ordering step was to measure at 1M and 10M before designing anything,
because every number above was extrapolated from 400,000 rows on SQLite. Done 2026-08-06
on PostgreSQL 15.8 against the corpus shape `benchmark_ontology_scale_postgres.py` seeds,
one observation per shape, each in a fresh process.

The extrapolation was wrong in the direction that mattered. SQLite predicted ~7.5 GB for a
filtered read at 10M. Postgres — the production dialect, and the one with no pushdown at
all — measured **21.9 GB**.

Before and after are the **same ten million rows**: the corpus was seeded once and reused,
so the only variable is the code.

| Shape at 10,000,000 objects | original | after B1/B2 | after B3/B4 | after materialized bounds |
| --- | ---: | ---: | ---: | ---: |
| Typed read, no filter — *what the gate measures* | 2.5 ms / 1.7 MB | 2.9 ms / 1.5 MB | 2.5 ms / 1.5 MB | 2.7 ms / 1.5 MB |
| Typed read, one filter — the Object Explorer | 157,654.5 ms / 21,940.6 MB | 8.2 ms / 1.6 MB | 3.4 ms / 1.7 MB | **2.8 ms / 1.5 MB** |
| Facet aggregation — the left rail | 163,095.2 ms / 21,935.0 MB | 138,681.6 ms / 6.8 MB | **40,957.8 ms / 1.4 MB** | 49,011.5 ms / 1.7 MB |
| Spatial radius — the Operational Map | 170,863.7 ms / 21,939.2 MB | 203,135.3 ms / 6.8 MB | 44,802.8 ms / 6.9 MB | 39,514.7 ms / 4.6 MB |
| Spatial bbox, map viewport — **the B4 gate** | — | — | — | **70.6 ms / 5.3 MB** |

The last column was measured while the test suite ran on the same host, so its latencies
are inflated — the facet's 49,011.5 ms against 40,957.8 ms is contention, not a
regression. The B4 gate passing under that load is the conservative direction; the facet
number is not, and 40,957.8 ms remains its recorded reading.

The viewport shape does not exist in the earlier columns because it was added with B4.
Its predecessor is the radius shape, which cannot express a selective viewport against
this fixture.

**Memory is fixed.** Every shape now costs single-digit megabytes at the scale Tier B
certifies, against 21.9 GB before — the Object Explorer no longer allocates more than a
commodity host has to click a filter.

**Latency.** After B1 the filtered read fell from 157.7 seconds to 8.2 milliseconds,
because its predicate reaches SQL and the `LIMIT` goes with it. The facet aggregation
improved 15% and the spatial query got **19% worse** — streaming with a per-row expunge
costs more per row than a bulk fetch, and neither shape could stop early. B3 and B4 then
addressed both: the facet is 3.4x faster and the spatial query 4.5x, more than reversing
its regression.

Both remain far from interactive at 41 s and 45 s, and both now have a measured cause
rather than a suspicion — see the conditions below. What closes them is an expression
index driven by the ontology's own `indexed` flag, and a materialized bounding box.

**What the B1 PASS covers.** The run used one cardinality, so the growth gates did not
execute; only the 64 MB absolute ceiling was checked. Growth was measured separately at
100k → 1M → 400k across dialects and is what the tables earlier in this document record.
A single-cardinality PASS is a weaker claim than B1 as written and the harness prints so.

### Two more defects, both invisible on SQLite

The repair had to be written twice for Postgres, and both faults were in the half of the
code SQLite never reaches:

- `properties.contains({field: value})` resolved to the **generic string `LIKE`**, not
  the JSONB `@>` operator. The column is `JSON().with_variant(JSONB(), "postgresql")`, so
  its Python-side comparator is `JSON`, which has no containment operator. Postgres
  rejected the statement outright — loudly, which is the only reason it was cheap.
- `properties[field].astext` does not exist for the same reason, so the `exists`
  predicate raised `AttributeError`.

Every SQLite test passed throughout. This is the same asymmetry that produced the original
defect: the pushdown existed only on the dialect nobody ships, so the dialect everybody
ships was the unoptimized one and nothing measured it.

## The spatial fixture placed ten million objects on a line

Found 2026-08-07. Every spatial number in this document before that date describes the
fixture rather than the system, and the correction is not an improvement to the product.

The seed set latitude to `37.0 + mod(series,1000)/10000` and longitude to the negation of
the same term. Both coordinates moved together, so the corpus was not a region at all: it
was **a thousand distinct positions on a single diagonal line**, with ten million objects
stacked ten thousand deep at each. A 400 m radius matched 570,000 of them. The query was
never finding objects; it was scoring a pile of coincident ones.

Replaced with a two-scale deterministic distribution over a ~55 x 44 km region: sites laid
out by an additive-recurrence (R2) low-discrepancy sequence, and each object at its own
offset within its site, because operational assets cluster at facilities rather than
spreading evenly. No random number generator, so the corpus is identical on every run and
on both dialects. One hundred thousand objects now occupy one hundred thousand distinct
positions.

Measured at one million objects, which is the size at which an old-fixture reading with
current statistics also exists, so only the distribution differs:

| Shape | old fixture | new fixture |
| --- | ---: | ---: |
| Spatial radius | 466.2 ms, **57,000 matched** | **10.4 ms, 549 matched** |
| Spatial bbox viewport | 10.5 ms, 1,000 matched | 10.0 ms, 791 matched |
| Typed read, no filter | 2.9 ms | 2.8 ms |
| Typed read, one filter | 5.1 ms | 6.0 ms |
| Facet aggregation | 2,368.8 ms | 5,271.5 ms |

**The radius query did not get 45x faster.** It stopped scoring 57,000 coincident points
and started answering a spatial question, returning 549 objects from one facility — which
is what an operator asks for. Read the row as a correction to the instrument, never as a
gain.

Two guards came with the fixture. The SQL and Python seed paths compute positions from the
same formula, since a divergence would have the two dialects measuring different corpora
under one name. And the object type records a `fixture_version` that `--reuse` checks: a
row count cannot tell two fixtures apart, and comparing a measurement against numbers from
a different fixture is precisely the error this section documents.

**Ten million on the new fixture is not measured**, because the load itself was diagnosed
first. Two attempts were abandoned; the first ran two hours to 27%, tracking roughly seven
hours where earlier ten-million loads took 36 to 41 minutes.

### Why the load is slow

Measured 2026-08-07 by timing committed batches of 500,000 rows, **with every geo index
dropped**:

| batch | rows loaded | rows/s |
| ---: | ---: | ---: |
| 1 | 500,000 | 10,416 |
| 2 | 1,000,000 | 7,812 |
| 3 | 1,500,000 | 4,950 |
| 4 | 2,000,000 | 3,521 |
| 5 | 2,500,000 | 2,873 |
| 6 | 3,000,000 | 2,645 |

Throughput decays fourfold with none of this goal's indexes present. **The GiST index is
not the cause**, and this is the second time that hypothesis was asserted and then
refuted — the first refutation, at one million, was worthless because at that size the
index fits in cache and could not have shown the effect either way.

The cause is that `object_instances` carries **2,761 MB of indexes against a 966 MB heap**
— 2.9 times more index than data — while `shared_buffers` is **128 MB**:

| index | size | origin |
| --- | ---: | --- |
| `ix_oi_property_e18d75ee…` | 552 MB | profile `indexed` flag |
| `ix_object_instances_materialized_active` | 459 MB | model |
| `ix_oi_property_33398485…` | 458 MB | profile `indexed` flag |
| `ix_object_instances_properties_gin` | 385 MB | `0027_ontology_query_indexes` |
| `ix_object_instances_project_type_updated_id` | 271 MB | model |
| `object_instances_pkey` | 261 MB | primary key |
| `ix_object_instances_id` | 261 MB | **redundant — duplicates the primary key** |

Every insert maintains all of them with random writes across 2.7 GB of index through a
128 MB buffer. WAL runs 8 to 25 MB/s against 1 to 3 MB/s of heap growth, roughly ninefold
amplification, which `wal_level = logical`, `max_wal_size = 1 GB` and `full_page_writes =
on` together explain — the container log had been warning "checkpoints are occurring too
frequently" throughout.

**244 indexes across the schema exactly duplicate their table's primary key, 283 MB in
total**, because every model declares `primary_key=True, index=True` and a primary key
already implies a unique index. That is a redundant index maintained on every insert to
every table, and it is the cheapest of these to remove.

None of this is caused by the read-path work in this goal. It is pre-existing, and it was
invisible while the spatial fixture was degenerate, because a corpus of a thousand
positions never grew an index large enough to leave cache.

## The harness never updated planner statistics

Found 2026-08-07, and it invalidates numbers reported earlier in this document rather
than merely refining them.

The fixture bulk-loads through `generate_series` and then measured immediately. Postgres
had no statistics for the new rows, so it estimated **one row** for the object type and
planned accordingly — filtering through the type index instead of using the GiST index it
had just been given. The harness was measuring what the planner did not know.

At one million objects, the identical corpus, before and after a single `ANALYZE`:

| Shape | stale statistics | current statistics |
| --- | ---: | ---: |
| Facet aggregation | 5,610.0 ms | **2,368.8 ms** |
| Spatial radius | 6,388.0 ms | **466.2 ms** |
| Spatial bbox viewport | 6,263.3 ms | **10.5 ms** |

A factor of 596 on the shape whose gate this document turns on. The B4 result at ten
million was not wrong — that run had a concurrent test suite giving autovacuum time to
analyze — but it was correct by accident, and the facet and radius figures at ten million
were measured on a corpus the planner did not understand.

`ANALYZE` now runs as part of seeding, because every real bulk load owes it too. It
belongs in the fixture rather than in a caveat.

This is the fourth instrument defect in this harness, and the same shape as the others:
nothing errored, the numbers looked plausible, and they were consistent enough across
sizes to read as a curve.

## A defect in the harness, found while building it

The first version of `measure_read_path_bounds.py` timed each query with `tracemalloc`
running, to collect latency and heap in one pass. `tracemalloc` hooks every allocation,
and these paths allocate per row, so it inflated the scanning shapes by roughly 3x —
the filtered read read 1,692.7 ms instead of 672.6 ms at 100k — and left the bounded
shape almost untouched, because it barely allocates.

The distortion pushed in the direction of the conclusion the harness was written to
reach. Nothing in the output would have shown it; the numbers were merely larger, and
larger was the expected shape. Someone acting on them would have optimized an artifact.

The passes are now separate, and the reason is a comment in the source rather than a
commit message, because the next person to combine them for speed needs to see it there.

It is worth noticing what it took to catch: not a test, but running the harness against a
shape whose answer was already known from a separate run. That is the same method that
caught the RPO sampler's 405 — dry-running an instrument against a known result — and it
is the only one that has reliably worked here.

Two more followed, both caught the same way, both silent:

**The memory instrument read zero.** Ported to resident memory for the Postgres run, it
called `GetProcessMemoryInfo` with an undeclared `GetCurrentProcess` restype. ctypes
handed back the pseudo-handle as a signed 32-bit int, the call failed, and the struct
stayed zeroed. Every shape at every size reported **0.0 MB** — which is precisely what a
bounded read looks like. The harness would have certified the defect as fixed before
anyone touched it. It now verifies itself against a known allocation on every run and
refuses to report if the reading does not move.

**The 10M run was measuring the fix.** The measurement was started in the background and
the repair was written while it ran. Each observation runs in a fresh subprocess, so every
query at 10M would have imported the edited `runtime.py` — a "before" number produced by
the "after" code, biased toward making the defect look smaller, in a table captioned as
the case for the work. Caught by asking what a subprocess imports, not by anything the
output showed. The run was discarded and re-measured against a stashed-clean tree.

The pattern across all three: **the reading looked right.** None produced an error, an
outlier, or a shape anyone would question. What separates a real number from a fabricated
one here is not inspection of the output but knowing what the instrument touched.

## How this goal gets gamed

- **Bounding the page instead of the query.** Capping the response at 500 rows while the
  scan still runs makes every number in the latency table unchanged and the API look
  tidy. The gate is peak heap and growth, not response size, for exactly this reason.
- **Measuring on SQLite.** The favorable dialect has a pushdown the production dialect
  does not. Every B1 reading is required on both.
- **Fixing the shapes that are measured.** Four shapes are named; the product issues
  more. B2 counts materialization sites in source, which does not care whether a shape
  appears in the harness.
- **Declaring a cap and calling it a total.** B3 permits a capped count only if the
  response says it is capped. A silently truncated total is worse than a slow one,
  because it is wrong rather than late.
- **Relabelling `renderable_base_types` and stopping.** The relabel is honest bookkeeping,
  not progress. B6's ratchet is the reach number, and it starts at 1 of 22.
- **Re-running B1 until a good host gives a clean curve.** The worst observation is the
  measurement, per the existing contract, and the growth bound is a ratio, so a uniformly
  fast host does not help.

## What this goal is not

It is not a performance-tuning project. Nothing here asks for a faster constant factor;
every condition asks for a different growth curve, which is a design change and not an
optimization. A change that makes the 400k spatial query take 3 s instead of 6.9 s has
satisfied nothing.

It is not a replacement for Tier B. Tier B's remaining gates — availability, RPO, RTO —
are blocked on wall clock and a pilot, and this goal does not touch them. It does change
what one satisfied gate should be read as claiming.
