# Goal — Bounded on the Path the Product Actually Takes

Stated 2026-08-06 on `codex/builder-ux-production`. This goal does not restate the
outcome, scope, or severity gate of [`GOAL_2026-08-03.md`](GOAL_2026-08-03.md); those
govern it. It adds a third invariant to [`GOAL_STANDING.md`](GOAL_STANDING.md) and a
program of work that discharges it.

## Why this goal exists

The Tier B ontology-scale gate passes at 10,000,000 objects and 50,000,000 links, with
lookup p95 8.916 ms, range p95 12.248 ms and two-hop p95 14.153 ms. The evidence file is
honest and current at head `0038`.

It measures a query shape the product never issues.

The gate reads an object set with no residual filter. Every surface a user actually
touches sends a filter, a facet, or a spatial predicate, and each of those takes a
different code path — one that loads the entire object type into memory first.

Measured 2026-08-06 by `oms/measure_read_path_bounds.py`, worst of three, on SQLite.
Growth is normalized to a 10x cardinality step, so a bounded read reads x1 and a read
that materializes the type reads x10:

| Query shape | 25,000 | 100,000 | 400,000 | per 10x |
| --- | ---: | ---: | ---: | ---: |
| **Latency** | | | | |
| Typed read, no filter — *the shape the gate measures* | 2.7 ms | 1.4 ms | **1.3 ms** | **x0.5** |
| Typed read, one equality filter — the Object Explorer | 110.0 ms | 672.6 ms | **2,235.1 ms** | **x12.2** |
| Facet aggregation — the Explorer's left rail | 314.1 ms | 1,993.4 ms | **6,390.3 ms** | **x12.2** |
| Spatial radius query — the Operational Map | 482.5 ms | 1,657.6 ms | **7,119.4 ms** | **x9.3** |
| **Peak heap, one request** | | | | |
| Typed read, no filter | 0.1 MB | 0.1 MB | **0.1 MB** | **x1.0** |
| Typed read, one equality filter | 19.1 MB | 75.6 MB | **302.5 MB** | **x9.9** |
| Facet aggregation | 57.3 MB | 228.0 MB | **912.8 MB** | **x10.0** |
| Spatial radius query | 57.3 MB | 228.0 MB | **912.8 MB** | **x10.0** |

The heap column is the finding. Three of the four shapes grow x9.9 to x10.0 per 10x
objects — memory proportional to the object type, exactly and not approximately — while
the measured shape is flat at x1.0.

Extrapolating from here put one Object Explorer filter click at roughly 7.6 GB and one map
render at roughly 22.8 GB at the 10,000,000 objects the gate certifies. Both were later
measured directly, on Postgres, and the filtered read came in at **21.9 GB** — nearly
three times the projection, because the production dialect had no pushdown at all where
SQLite narrowed the candidate set first. The measured table is below; this one is kept
because it is what prompted the work and because the projection it supported was wrong in
a direction worth remembering.

This is not a platform that is slow at scale. It is a platform that dies at the scale its
own evidence file certifies, on every path except the one that was measured.

Two details make the reading worse rather than better:

- The measurement ran on **SQLite, the favorable dialect**. `_pushdown_equalities` returns
  `[]` for every dialect except SQLite, by design and with a comment saying Postgres
  pushdown is "a later hardening step". Production is Postgres, where the filtered read
  has no pre-filter at all and materializes the whole object type rather than the
  matching third.
- `_logic_object_rows` calls `.all()` and applies its `limit` argument to the resulting
  Python list. The limit never reaches SQL. So a call site asking for **five** rows loads
  the entire object type, and all twenty-one call sites are unbounded regardless of what
  they pass.

## The finding this generalizes to

The gate is not wrong and its evidence is not stale. Neither standing invariant fires:
the proof is current at the head, and the extensibility ratchets are green. The claim is
false anyway, because **the measurement entered the system somewhere the product does
not**.

The same shape appears a second time, independently, in this session's other reading. The
extensibility audit reports `semantic types the UI can render 13 of 13`. All thirteen
hits come from one file — `frontend/src/utils/semanticRender.tsx`, the renderer itself.
Exactly one workspace of twenty-two imports it. The audit would still read 13 of 13 if no
component consumed it at all, because it measures the renderer's vocabulary and not its
reach. The Operational Map — the surface where a `geopoint` and a `geoshape` most
obviously belong — passes raw properties to `KeyValueGrid` with no specs, so a polygon
still reaches the user as GeoJSON text.

Two instruments, both honest about what they measured, both certifying a product property
that does not hold, for the same reason: **a component measured in isolation says nothing
about the composition that ships.**

## The invariant

Added to [`GOAL_STANDING.md`](GOAL_STANDING.md) as the third:

> **A measurement is evidence only for the path it traverses.** Every gate names the entry
> point it enters through and the request shape it issues. A gate that enters below the
> product's own entry point states, in its evidence file, what it therefore does not
> cover.

This is not a restatement of "no claim outlives its proof". That invariant asks whether
the proof is current. This one asks whether the proof is *about the product*. A gate can
be re-run every commit, at the current head, forever, and still certify nothing a user
will experience.

## Ending conditions

Numeric, measured on the reference profile at three cardinalities — 100k, 1M and 10M —
and on both dialects. Every condition carries an evidence file in the envelope defined by
[`TIER_B_MEASUREMENT_CONTRACT.md`](TIER_B_MEASUREMENT_CONTRACT.md).

### B1 — Reads are bounded by the page, not by the object type

For each of four shapes — unfiltered read, filtered read, facet aggregation, spatial
predicate — across each 10x cardinality step:

- peak heap per request grows **≤ 1.5x**, and
- p95 latency grows **≤ 2x**, and
- peak heap per request stays **≤ 64 MB** at every cardinality.

The growth bounds are the real gate; they are host- and dialect-independent, and they are
what "bounded" means. The absolute ceiling is a backstop against satisfying the growth
bound at a uniformly terrible constant.

The reading that opened this condition, from `oms/measure_read_path_bounds.py`, which
implements it and exits non-zero: heap grew **x10.0** per 10x against a x1.5 bound, latency
**x12.2** against a x2.0 bound, and peak heap reached **912.8 MB** against 64 MB — at
400,000 objects, 4% of the certified scale.

**Memory now satisfies this condition; latency does not.** At 10M on Postgres every shape
sits at or under 6.8 MB. The growth bounds hold for the unfiltered and filtered reads, and
fail for the facet aggregation and the spatial query, both of which still visit every row.
B1 is therefore **partially met** and stays open until B3 and B4 land.

### B2 — No route can materialize an object set — **met**

`oms/audit_query_bounds.py` reports **0** object-set materializations whose size is a
function of object-type cardinality, reachable from an HTTP route, down from 24. Ratcheted:
the count may fall and never rise.

The audit derives each primitive's status from its own source every run rather than
carrying a hand-maintained verdict, so a primitive that stops streaming re-fails the build
without anyone remembering to update a constant. The chaos gate's hand-maintained zero is
why that matters.

Baseline **24**, across 9 modules — 21 via `_logic_object_rows`, 3 via
`_query_object_rows`. The affected modules were not a corner of the system:
`object_explorer_ops` (the primary object UI), `gis_ops` (the map), `mcp_tools` (the MCP
surface other programs consume), `quiver_runtime` (analytics), `slate_runtime` and
`workshop_runtime` (the surfaces for building applications on the ontology),
`notepad_ops`, `aip_agents`, `runtime`.

### B3 — Exact totals do not cost a scan

No route returns an exact total that requires materializing the set. Each total is either
a SQL `count(*)`, or a capped count declared as capped in the response.

This condition exists because it is the *cause* of the other twenty-four. The reason call
sites pass `limit=10 ** 9` is that `_logic_object_rows` returns `len(matched)` alongside
the rows, and an exact total over a filtered set is only obtainable by filtering
everything. The API contract forces the scan; fixing the call sites without fixing the
contract will reintroduce it.

### B4 — Spatial predicates are evaluated in the database

A bounding-box pre-filter runs in SQL on both dialects, backed by an index, before any
Python geometry work. Haversine refinement over the candidate set is fine; scanning the
type is not. Gate: bbox query p95 **< 250 ms** at 10M objects.

This is also the precondition for the GIS work already on the roadmap. A spatial platform
whose spatial query is a Python loop over every row does not acquire scale by adding
layers on top.

### B5 — Predicate pushdown is not dialect-specific

Equality, comparison and existence predicates push into SQL on Postgres as well as
SQLite, with a measured Postgres reading for every shape in B1. Where a predicate cannot
push down, the route declares the residual and bounds the candidate set rather than
materializing it.

### B6 — Semantic rendering reaches every surface that shows object properties — **met**

New ratchet in `oms/audit_extensibility.py`: **data surfaces receiving declared specs, of
surfaces rendering ontology object properties.** `DataTable` gains a specs parameter;
`KeyValueGrid` call sites that render object properties pass them; the Map inspector
included.

The verified baseline is the numerator: **one** surface receives specs, `ObjectExplorer`,
and it is the only one of twenty-two workspace modules that imports the renderer at all.
The denominator is not yet established — most of those twenty-two render operational or
configuration data, where a generic formatter is correct, so counting all of them would
overstate the gap. Fixing the denominator is part of building the instrument, and it is
stated here as unknown rather than guessed.

The existing `renderable_base_types` reading stays but is relabelled as vocabulary, not
reach, so that 13 of 13 stops reading as a coverage claim.

### B7 — The scale gate enters through the product's door

The Tier B ontology-scale harness issues its reads through `/api/v1`, using the request
shapes the Object Explorer and the Operational Map issue — including at least one filter,
one facet aggregation and one spatial predicate — and its evidence file names the entry
point and the shapes.

Until B7 lands, the Tier B ontology-scale row carries an explicit note that it certifies
the unfiltered shape only. The gate keeps its PASS: its evidence is accurate about what it
measured. What was wrong was the inference drawn from it, and the fix for a wrong
inference is to state the scope, not to delete the measurement.

## Measured at reference scale, and repaired

Condition B1's first ordering step was to measure at 1M and 10M before designing anything,
because every number above was extrapolated from 400,000 rows on SQLite. Done 2026-08-06
on PostgreSQL 15.8 against the corpus shape `benchmark_ontology_scale_postgres.py` seeds,
one observation per shape, each in a fresh process.

The extrapolation was wrong in the direction that mattered. SQLite predicted ~7.5 GB for a
filtered read at 10M. Postgres — the production dialect, and the one with no pushdown at
all — measured **21.9 GB**.

Before and after are the **same ten million rows**: the corpus was seeded once and reused,
so the only variable is the code.

| Shape at 10,000,000 objects | latency before | latency after | memory before | memory after |
| --- | ---: | ---: | ---: | ---: |
| Typed read, no filter — *what the gate measures* | 2.5 ms | 2.9 ms | 1.7 MB | 1.5 MB |
| Typed read, one filter — the Object Explorer | 157,654.5 ms | **8.2 ms** | 21,940.6 MB | **1.6 MB** |
| Facet aggregation — the left rail | 163,095.2 ms | 138,681.6 ms | 21,935.0 MB | **6.8 MB** |
| Spatial radius — the Operational Map | 170,863.7 ms | 203,135.3 ms | 21,939.2 MB | **6.8 MB** |

**Memory is fixed.** Every shape now costs single-digit megabytes at the scale Tier B
certifies, against 21.9 GB before — the Object Explorer no longer allocates more than a
commodity host has to click a filter.

**Latency is fixed for one shape of three.** The filtered read fell from 157.7 seconds to
8.2 milliseconds because its predicate now reaches SQL and the `LIMIT` goes with it. The
facet aggregation improved 15% and the spatial query got **19% worse** — 170.9 s to
203.1 s. That is not a rounding artifact and it is not hidden here: streaming with a
per-row expunge costs more per row than a bulk fetch, and neither shape can stop early,
because one owes an exact total over every group and the other has no spatial index to
narrow candidates before Python evaluates geometry. Those are conditions B3 and B4, and
they remain open. Trading 19% of latency on one shape for a 3,226-fold cut in memory is
worth it at this scale, but it is a trade and not a win.

**What the B1 PASS covers.** The run used one cardinality, so the growth gates did not
execute; only the 64 MB absolute ceiling was checked. Growth was measured separately at
100k → 1M → 400k across dialects and is what the tables earlier in this document record.
A single-cardinality PASS is a weaker claim than B1 as written and the harness prints so.

### Two more defects, both invisible on SQLite

The repair had to be written twice for Postgres, and both faults were in the half of the
code SQLite never reaches:

- `properties.contains({field: value})` resolved to the **generic string `LIKE`**, not
  the JSONB `@>` operator. The column is `JSON().with_variant(JSONB(), "postgresql")`, so
  its Python-side comparator is `JSON`, which has no containment operator. Postgres
  rejected the statement outright — loudly, which is the only reason it was cheap.
- `properties[field].astext` does not exist for the same reason, so the `exists`
  predicate raised `AttributeError`.

Every SQLite test passed throughout. This is the same asymmetry that produced the original
defect: the pushdown existed only on the dialect nobody ships, so the dialect everybody
ships was the unoptimized one and nothing measured it.

## Ordering

1. ~~**Measure at reference scale first.**~~ **Done 2026-08-06.** The caution was
   warranted: the SQLite extrapolation understated Postgres roughly threefold.
2. ~~**Push down**~~ **(B5) done for equality and existence on both dialects.** Ordered
   comparisons deliberately stay in the Python pass, because `_compare_filter` coerces
   with `float()` and no SQL dialect reproduces that. Streaming made them affordable.
3. ~~**Wire the renderer** (B6).~~ **Done 2026-08-06.**
4. **Fix the contract** (B3). Fourteen call sites still ask for everything because the
   exact total is only available by scanning. This is now the binding constraint on
   latency for the facet aggregation, and fixing the call sites individually leaves the
   incentive in place — the contract has to change.
5. **Index the spatial predicate** (B4). The spatial query is the one shape the repair
   made slower, and no amount of streaming fixes it: without a bounding-box pre-filter in
   SQL, every row reaches Python before its geometry is judged.
6. **Re-scope the gate** (B7), once there is something worth measuring through the door.

## A defect in the harness, found while building it

The first version of `measure_read_path_bounds.py` timed each query with `tracemalloc`
running, to collect latency and heap in one pass. `tracemalloc` hooks every allocation,
and these paths allocate per row, so it inflated the scanning shapes by roughly 3x —
the filtered read read 1,692.7 ms instead of 672.6 ms at 100k — and left the bounded
shape almost untouched, because it barely allocates.

The distortion pushed in the direction of the conclusion the harness was written to
reach. Nothing in the output would have shown it; the numbers were merely larger, and
larger was the expected shape. Someone acting on them would have optimized an artifact.

The passes are now separate, and the reason is a comment in the source rather than a
commit message, because the next person to combine them for speed needs to see it there.

It is worth noticing what it took to catch: not a test, but running the harness against a
shape whose answer was already known from a separate run. That is the same method that
caught the RPO sampler's 405 — dry-running an instrument against a known result — and it
is the only one that has reliably worked here.

Two more followed, both caught the same way, both silent:

**The memory instrument read zero.** Ported to resident memory for the Postgres run, it
called `GetProcessMemoryInfo` with an undeclared `GetCurrentProcess` restype. ctypes
handed back the pseudo-handle as a signed 32-bit int, the call failed, and the struct
stayed zeroed. Every shape at every size reported **0.0 MB** — which is precisely what a
bounded read looks like. The harness would have certified the defect as fixed before
anyone touched it. It now verifies itself against a known allocation on every run and
refuses to report if the reading does not move.

**The 10M run was measuring the fix.** The measurement was started in the background and
the repair was written while it ran. Each observation runs in a fresh subprocess, so every
query at 10M would have imported the edited `runtime.py` — a "before" number produced by
the "after" code, biased toward making the defect look smaller, in a table captioned as
the case for the work. Caught by asking what a subprocess imports, not by anything the
output showed. The run was discarded and re-measured against a stashed-clean tree.

The pattern across all three: **the reading looked right.** None produced an error, an
outlier, or a shape anyone would question. What separates a real number from a fabricated
one here is not inspection of the output but knowing what the instrument touched.

## How this goal gets gamed

- **Bounding the page instead of the query.** Capping the response at 500 rows while the
  scan still runs makes every number in the latency table unchanged and the API look
  tidy. The gate is peak heap and growth, not response size, for exactly this reason.
- **Measuring on SQLite.** The favorable dialect has a pushdown the production dialect
  does not. Every B1 reading is required on both.
- **Fixing the shapes that are measured.** Four shapes are named; the product issues
  more. B2 counts materialization sites in source, which does not care whether a shape
  appears in the harness.
- **Declaring a cap and calling it a total.** B3 permits a capped count only if the
  response says it is capped. A silently truncated total is worse than a slow one,
  because it is wrong rather than late.
- **Relabelling `renderable_base_types` and stopping.** The relabel is honest bookkeeping,
  not progress. B6's ratchet is the reach number, and it starts at 1 of 22.
- **Re-running B1 until a good host gives a clean curve.** The worst observation is the
  measurement, per the existing contract, and the growth bound is a ratio, so a uniformly
  fast host does not help.

## What this goal is not

It is not a performance-tuning project. Nothing here asks for a faster constant factor;
every condition asks for a different growth curve, which is a design change and not an
optimization. A change that makes the 400k spatial query take 3 s instead of 6.9 s has
satisfied nothing.

It is not a replacement for Tier B. Tier B's remaining gates — availability, RPO, RTO —
are blocked on wall clock and a pilot, and this goal does not touch them. It does change
what one satisfied gate should be read as claiming.
