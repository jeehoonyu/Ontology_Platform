# Goal — Drag with a mouse, or reach it some other way

Stated 2026-08-19. Follows [`GOAL_UI_ENHANCEMENT_2026-08-18.md`](GOAL_UI_ENHANCEMENT_2026-08-18.md),
which answered the framework question and left the hardest interaction in the product
unmeasured.

## The question, answered again and then narrowed

*Is it possible to change to React, and is React more beneficial for a complicated
drag-and-drop UI?*

**There is nothing to change to.** `frontend/package.json` names `react` 19.2.3 and
`react-dom` 19.2.3; the twenty-two workspaces are `.tsx`; the build is Vite with
`@vitejs/plugin-react`. The prior goal set this out with the dependency list rather than
an opinion and it has not changed.

The second half of the question is the useful one, and the honest answer is that **React
is not the variable**. A browser fires `dragstart` the same way whatever renders the
element. What decides whether a complicated drag works is the *mechanism*, and this
interface runs three at once:

| Mechanism | Sites | |
| --- | --- | --- |
| native HTML5 `draggable` + `dataTransfer` | **4** | `OntologyManager` ×2, `PipelineBuilder`, `VisualBuilder` |
| `@dnd-kit` `useSortable` | **1** | `VisualBuilder` node inspector |
| `@xyflow/react` node dragging | **3 canvases** | `OntologyManager`, `PlatformGraph`, `VisualBuilder` |

**That table is wrong, and the section at the bottom of this document says how.** There
were four mechanisms. The fourth is left out of the count here rather than quietly
corrected, because the reason it was missed is the more useful part.

So if there is leverage anywhere near this question, it is in the four hand-rolled ones —
and specifically in one fact about the platform, not about the framework:

> **Native HTML5 drag-and-drop does not fire from touch input, and is not operable from
> the keyboard.** A finger on `<button draggable>` scrolls the page. No care in the
> handler changes it.

`touch-authoring.spec.ts` had already measured that on the pipeline builder in the
previous goal: palette and canvas both visible, and neither a tap nor a touch-drag
produced a node. What nothing had done was ask the same question of the other three.

## Finding — the alternatives existed, and nothing held them in place

Three of the four native drags already had a second control. `OntologyManager`'s mapping
panel has a select beside every target property; its property rows have `Up` and `Down`;
`VisualBuilder`'s library entries are buttons with an `onClick` that places the node.

**None of them was operated by any test.** That is the defect, and it is a quieter one
than a missing control: the next person to tidy a screen could delete a stray `onClick`,
watch the whole suite stay green, and leave a workspace usable only with a mouse. That
path was walked deliberately to check — removing `onClick={() => addNode(item.type)}`
from `VisualBuilder`, rebuilding, and confirming the new test says *tapping a library
entry placed no node, so the canvas is drag-only*.

Every one of the four new tests has been shown to fail when the thing it defends is
removed — the `onClick`, the mapping select's `onChange`, the `Down` button's, and the
grip's `touch-action` — because a test that has never failed is a test whose failure mode
is unknown. Two of them were checked in the same build, which also confirmed the other two
stayed green: a break in one screen must not be what turns another red.

## Correction — the library-backed drag was the broken one

The tidy conclusion from all of the above is that `@dnd-kit` is the safe mechanism and the
four native drags should migrate onto it. Measuring disproved it before it could be
written down.

`@dnd-kit`'s pointer sensor does support touch. The one place this product uses it did
not work from a finger **at all**: `.drag-grip` carried no `touch-action: none`, so the
browser claimed each gesture for scrolling before the sensor saw a pointer move. A
configuration field could not be reordered on a phone.

| `.drag-grip` | Touch drag of row 1 past row 2 |
| --- | --- |
| as committed | nothing moved |
| with `touch-action: none` | reordered |

Measured with real touch points through CDP, because `page.touchscreen` taps and does
nothing else, and because a hand-fired `touchmove` does not produce the pointer events the
sensor listens for. One CSS line; the finding took the measurement.

The lesson is worth more than the fix. **"The library supports touch" and "this screen
works from a finger" are different claims**, and the first was true here throughout. A
migration onto `@dnd-kit` — the obvious, tidy, framework-flavoured answer to the original
question — would have moved four working-with-a-mouse drags onto the one mechanism that
was silently broken, and it would have looked like a cleanup.

## Second finding — adding tests broke a measurement, and that was the measurement's fault

The full tier passed with the new specs in it. The next `verify.py --fast` failed eleven
route-cost ceilings with no code between the two runs.

`route-cost.spec.ts` writes `frontend/route-cost.json`, and inside a full suite run it
executes after every stateful spec has seeded the database — including, now, the four
tests above. Every screen then issues more calls against more rows:

| | Isolated | After the suite seeded data |
| --- | --- | --- |
| map | 25 requests | **38** |
| pipeline | 12 requests | **19** |
| models | 15 requests | **22** |
| 16 routes | 223 requests | 264 |

Those numbers are real; they just describe a database rather than a build. The artifact was
being overwritten with them, and the next fast run judged the overwrite.

This is the **second** correction of exactly this shape on this one measurement.
[J4](GOAL_UI_ENHANCEMENT_2026-08-18.md) fixed it reusing one browser page, which measured a
warm cache; a fresh context per route removes what the previous *page* left behind and does
nothing about what the previous *spec* left in the database. The run inside the suite now
stays as coverage and writes nothing; `measure_route_cost.py` sets `ROUTE_COST_MEASUREMENT`
when it wants the file, the artifact records that it was taken that way, and
`audit_route_cost` refuses one that does not — saying which of the two silences it means,
because "not measured here" is not something a reader can act on.

The right-hand column is worth a second look on its own: **these screens fan out with data
volume.** A map that makes 25 calls against an empty database and 38 against a seeded one
is doing per-entity reads from the browser — the client-side shape of the write-side loop
the request-cost goal removed. That is not fixed here and is not claimed to be.

## Conditions

- **L1 — Answer the framework question from the dependency list, not from taste.**
  **Met** — React 19.2.3 is already the product, and the three drag mechanisms above are
  what the question was actually about. Restated here only because the question was asked
  again; the argument lives in the prior goal and is not duplicated.
- **L2 — Count the drags mechanically, so the list cannot fall behind the source.**
  **Met** — `oms/audit_drag_affordances.py` scans `frontend/src/**/*.tsx` and keys each
  drag by the payload it carries — a `dataTransfer` MIME type, or the state setter it
  calls when there is none — because line numbers move and ordinary reformatting rewrites
  the markup around them. [`DRAG_AFFORDANCES.md`](DRAG_AFFORDANCES.md) is generated from
  that scan and the gate fails if the committed file disagrees.

  *Superseded by L6.* Once there are no native drags left there is no payload to key on,
  and the audit gates the mechanism instead. The census this describes is also the one that
  missed a mechanism, which is recorded below rather than edited out.
- **L3 — No native drag is the only way to do what it does.** **Met** — all four declare
  an alternative. A fifth `draggable` with nothing declared fails the gate, naming the
  file and line, because a new drag is exactly when a screen goes mouse-only by accident:
  the author is at a desk, and the drag works.
- **L4 — Every alternative is operated by a finger, not asserted.** **Met** —
  `frontend/tests/drag-affordances.spec.ts`, on a 390×844 viewport with `hasTouch`, four
  tests plus the pipeline one already in `touch-authoring.spec.ts`. Each declaration names
  the spec *and the test title*, and the gate checks the spec still contains it, so
  renaming a test away from its claim fails rather than quietly stopping proving it. The
  specs are also checked for `dragTo` and `dragAndDrop`: a spec that drags cannot be
  evidence that a drag is unnecessary.
- **L5 — The library-backed drag is measured, not assumed.** **Met** — and it is why this
  condition exists. `SENSOR_BACKED` holds the same rule in a different shape: no
  alternative control is owed, because the sensor is meant to handle touch, but a touch
  drag in a browser is. The screen that most looked like it needed no test was the one
  that failed it.

## The migration, taken 2026-08-20

The section above says the migration onto `@dnd-kit` is a real option not taken, and that if
taken it should be taken with these tests already green. It was, and they were. What it
found is the reason the section is not simply deleted.

### The census was wrong: there were four mechanisms, not three

`audit_drag_affordances` counted native HTML5, `@dnd-kit` and `@xyflow/react`. It missed a
fourth, and missed it because of how it looked rather than what it did: pipeline nodes were
positioned by `onPointerDown` with `setPointerCapture`, hand-rolled in
`components/canvas/PipelineCanvas.tsx`. That is neither a `draggable` attribute nor a
sensor library, so no pattern matched it.

It was the worst of the four. It worked from touch — pointer events fire for touch and
`.pipeline-node` already carried `touch-action: none` — and it could not be reached from a
keyboard, and **a node's position had no second control anywhere**. Every other drag in
this product had one. The layout of a pipeline was mouse-and-finger only, and the audit
written to find exactly that reported three mechanisms and a clean bill.

A census that reports a number it did not measure is worse than no census.

### And the rule written to catch it caught only what was already gone

The first version of that rule was `setPointerCapture(|onPointerMove={` — which is to say,
verbatim the two lines the migration had just deleted. An adversarial review of this diff
found two ordinary ways back in that it scanned clean:

| Reintroduction | First rule | Now |
| --- | --- | --- |
| `useEffect` + `window.addEventListener("pointermove", …)` | missed | caught |
| `onMouseDown` / `onMouseMove` / `onMouseUp` in JSX | missed | caught |

The first of those is not an exotic spelling — it is the standard way to hand-roll a drag
that survives the pointer leaving the element, chosen *instead of* `setPointerCapture`.
Neither form trips any other rule here either: with no dnd-kit hook the file owes no
`SENSOR_BACKED` entry and never appears in the reference, so it is invisible to the whole
audit while the census prints **0 hand-rolled**. That is this file's own stated failure
mode, one level up.

`onMouseDown=` alone stays deliberately unmatched: three modal backdrops use it to close on
an outside press, and those are not drags. Both evasions and all three backdrops are now
assertions in the suite.

### Two bugs in the migration, and how they were caught

Both were caught by the same discipline: run the new test against a build with the thing it
defends removed.

**The keyboard test passed with its own wiring deleted.** It asserted on the node's bounding
box, and an arrow key scrolls a container — which moves the box without moving the node. It
reads `style.left`, the committed position, now.

**Then, fixed, it still failed with the wiring restored.** `useWorkspaceSensors` passed
`sortableKeyboardCoordinates` to every context. That getter derives the next position from
the other items in a `SortableContext`; outside one there are no other items and it returns
nothing, so **keyboard dragging on both canvases was inert** while every pointer drag worked
perfectly. The hook takes a `kind` now. Had the first version of the test been kept, the
migration would have shipped its headline capability broken, with a green test asserting it.

### What the migration actually bought

| | Before | After |
| --- | --- | --- |
| Drag mechanisms | 4 | 1, plus xyflow |
| Drags reachable by keyboard | **0** | all 5 |
| Node position on the pipeline canvas | mouse and finger only | keyboard too |
| Uncommitted position writes per node drag | one per pointer move | one, at the end |

Touch is deliberately *not* universal. The shared sensors take no touch gesture except on an
explicit grip, because a finger on a palette or a long property list is scrolling, and
trading that for a drag people have a button for is a bad trade. Touch reaches those
interactions through the control beside the drag, which is what the four tests above check.

- **L6 — One drag mechanism, and the gate refuses the others.** **Met** — 0 native HTML5,
  0 hand-rolled pointer, 4 files through `components/dnd/DragKit`, 3 xyflow canvases left
  alone. The gate names all three escapes, including the one that hid.
- **L7 — Every `DndContext` takes the shared sensors.** **Met** — a context configured by
  hand loses the 8px activation distance, and every draggable here is also a button that
  does the same job on click, so losing it does not break the drag; it breaks the control
  beside it. `VisualBuilder`'s inspector context was built that way and is the reason this
  is gated rather than assumed.
- **L8 — The drag itself is operable from a keyboard, and it is measured.** **Met** —
  `a pipeline node moves with the keyboard`, on the interaction that had no second control.
  Shown to fail twice: once with the listeners removed, once with the sensors misconfigured.

## What this is not

Not a migration onto one drag library. That is a real option, it would remove the whole
native class, and the correction above is the argument for not reaching for it first:
what makes a drag reachable is the measurement, not the dependency. If it is taken later
it should be taken with these five tests already green, so that a rewrite has to keep
what is now known to work.

Not a claim that the four native drags are good. A mouse user dragging a dataset field
onto a property is a fine interaction and worth keeping; it is being kept, and it is no
longer the only way in.

And not a general touch-support claim. Five interactions are proven from a finger. The
rest of the interface has the render sweep at four widths and nothing more, which is a
smaller claim than it sounds and is stated that way on purpose.
