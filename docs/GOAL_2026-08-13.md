# Goal — Enforcement That Has Never Run Is Not Enforcement

Stated 2026-08-13 on `master`, immediately after merging 89 commits into it.

## The finding

This project holds its product to an unusually strict standard. Ten Tier B gates carry
machine-readable evidence with a migration head, a harness, entry points and request
shapes. Ratchets fail the build when the corpus rots. The standing goal's first invariant
is *no claim outlives its proof*, and this repository applies it to reads, writes,
recovery, collaboration, identity and durability.

It has never applied it to the enforcement layer itself.

**GitHub Actions has never completed a run on this repository.** Fourteen runs, from
2026-07-26 to 2026-08-13, every one a failure. Every job across every workflow dies in
2–10 seconds with **zero steps executed** — the jobs are created and correctly named, so
the YAML parses; the runner never provisions. One of those failed runs is titled *"Add
automatic production CI gates"*.

So the sentence written into `ci.yml` beside the extensibility ratchet — *"catching it
here is the difference between a ratchet and an intention"* — describes something that has
never happened. The catching is the intention.

## What this actually costs

Not everything is exposed. Most ratchets have a `test_*.py` wrapper that applies them to
the live tree, and those run in the 211-script suite:

| Evidence corpus ratchet | `test_evidence_corpus_audit.py` — scans the live corpus, asserts the ceiling | yes, locally |
| Extensibility ratchets | `test_extensibility_audit.py` | yes, locally |
| Schema freeze | `test_schema_freeze.py` | yes, locally |
| Route coverage | `test_api_v1_route_coverage.py` | yes, locally |

| **Tier B audit** | nothing | **no** |
| **Docs conformance validator** | `test_docs_conformance.py` covers the logic; the validator itself is CI-only | partly |

The larger hole is the harnesses. **Eleven scripts hard-require a PostgreSQL
`DATABASE_URL`** and eleven more rehearsals and verifiers exist only as CI steps. Of the
24 distinct checks `ci.yml` invokes, these have **no automated execution anywhere**:

They ran during the 2026-08-09 session only because a human or an agent typed the command.
Nothing schedules them, nothing notices when they stop, and nothing recorded that they ran.

The frontend typecheck and build, the four-viewport WCAG matrix, Compose validation and
the multi-stage container build are in the same position — they are CI jobs, and CI does
not run. **89 commits merged to `master` on 2026-08-13 with none of that ever having
executed automatically.**

## The asymmetry worth naming

Every gate in this repository records *when it was measured, against what, at which head*.
No check records anything. `audit_evidence_corpus.py` prints "Ratchet held" and exits 0,
and that sentence has no timestamp, no head, and no memory. Ask "when did the query-bounds
ratchet last hold?" and the honest answer is that nobody can tell you.

That is the same defect the Tier B envelope was built to prevent, one level up. A gate
without provenance cannot be shown to be stale, so it never expires. A *check* without
provenance cannot be shown to have stopped running, so its silence is indistinguishable
from its success.

## What C5 and C6 mean concretely

A check writes a small record when it runs — `docs/enforcement-runs.jsonl`, one line per
execution, carrying the check's name, the migration head, the timestamp, the verdict, and
whether it ran locally or in CI. `audit_enforcement.py` then reports each declared check
as **CURRENT**, **STALE** (last ran at an older head), or **NEVER** — the same three
states the evidence corpus already uses for gates, applied to the instruments instead.

That turns today's invisible failure into a visible one. A ratchet nobody has run since
`0038` would read STALE and say so, rather than reading as a green build that never
happened.

### Correction, made while building it: the ratchet is on NEVER, not CURRENT

C6 originally said the ratchet was "the count of checks reading CURRENT: it may rise and
must never fall". That is wrong, and building it showed why within minutes. Advancing the
migration head makes *every* check stale at once, so the CURRENT count drops to zero and
the build breaks until each is re-run — on every migration, as a matter of routine.

This repository already learned that lesson from the other direction. The Tier B gate step
is deliberately `continue-on-error`, with the reason written beside it: *"gating on it
would leave the build permanently red and train everyone to ignore it."* A ratchet that
fires during ordinary work does not get obeyed; it gets routed around, and then it is
decoration.

So **staleness is reported and never gates. What gates is regression to NEVER**: once a
check has been shown to run, it must keep having run. That is stable across migrations and
still catches the failure this goal exists for — a check quietly dropping out of every
automated path. Both behaviours were verified rather than assumed: deleting a check's
record exits 1 and names it; back-dating every record to an older head reports 8 STALE and
exits 0.

### Implemented 2026-08-13

`oms/enforcement_runs.py` declares the eight checks and records each run —
verdict, migration head, timestamp, and whether it ran locally or in CI, since
"it passes on my machine" and "it passes in CI" are different claims and this
repository has only ever been able to make the first. `oms/audit_enforcement.py`
reports and ratchets. `docs/enforcement-runs.json` holds one entry per check, latest
run only: an append-only journal would add a line to every diff on every local
invocation, and the question here is only *when did this last run*.

Runs are recorded on failure and on a crash, not only on success. A check that fails every
time would otherwise be indistinguishable from one that never executes, which is the
confusion this goal is named after.

The first audit, before any check had recorded anything, read **8 declared, 0 ever run** —
the honest state of a repository whose CI has never provisioned a runner. After running
all eight: 8 CURRENT, floor set at 8.

`oms/test_enforcement_runs.py` (22 assertions) tests the module *and* applies the live
ratchet, so the auditor has an automated home in the suite. Building it as another CI-only
script would have reproduced the exact defect under repair.

## C2 closed 2026-08-13, and the baseline in this document was wrong

C2 said "11 undeclared". The real surface is **35 check-shaped scripts**, and the count
was wrong because the classification behind it was. It treated "the script's name appears
in a test file" as coverage. It is not: every benchmark and verifier here has a contract
test that reads its source with `read_text` and asserts things *about* it — genuinely
useful, and not the same as running it. Nine checks looked covered for exactly that
reason. `check_registry.suite_executions` now counts an `import`, not a mention.

`oms/check_registry.py` declares each script's claim and cadence and **infers its
requirements from source**, so a check that grows a PostgreSQL dependency cannot keep a
declaration saying it needs nothing. `oms/audit_check_coverage.py` separates two failures
that need different fixes:

- **UNDECLARED** — a check nobody wrote down.
- **UNAUTOMATED** — a check that needs no infrastructure and still has no home. Not a
  declaration problem, a defect.

| | before | after |
| --- | ---: | ---: |
| UNDECLARED | 1 | **0** |
| UNAUTOMATED | 2 | **0** |
| SUITE — a test executes it | 5 | **10** |
| CI only | 3 | **1** |
| MANUAL — declared, needs infrastructure | — | 24 |

Four checks were fixed rather than documented. `audit_query_bounds` — a ratchet the
standing goal names by title — was in no workflow and no test at all. `validate_docs_conformance`,
`validate_tier_b_evidence` and `validate_external_evaluations` were reachable only from a
CI that has never provisioned a runner. All four now run in `oms/test_check_homes.py`
(46 assertions), which makes them independent of C1.

Two of them legitimately exit nonzero — Tier B stands at 7 of 10, and no external team has
submitted an evaluation. They are required to **complete**, not to pass. Asserting
otherwise would assert that unfinished work is finished, which is what the Tier B step's
`continue-on-error` already avoids for the same reason.

The audit found a defect in its own registry on first run: the new check was keyed
`check_coverage` while the file is `audit_check_coverage.py`, and it reported itself
UNDECLARED. Both ratchets were then verified by breaking them — adding an undeclared
verifier exits 1 and names it; removing a check's suite home exits 1 and reports it
UNAUTOMATED.

C3 and C4 are absorbed by this: `audit_query_bounds` and `validate_tier_b_evidence` both
run in the suite now. The single remaining CI-only check is `benchmark_pipeline_scale`,
which is correct — its smoke profile belongs on every push and its reference profile does
not.

## C1 diagnosed 2026-08-13: it is a billing block, and it is not fixable from here

The earlier guess in this document — "most likely exhausted minutes, a spending limit, or
Actions disabled" — was a guess. GitHub says it outright. Every failed run carries an
annotation, identical on each one sampled from 2026-08-12 back through the series:

> The job was not started because recent account payments have failed or your spending
> limit needs to be increased. Please check the 'Billing & plans' section in your settings

Facts that narrow it further: the repository is **private**, so free-tier minutes apply;
Actions is **enabled** with all actions allowed; and the failures span 2026-07-26 to
2026-08-13, straddling a monthly quota reset that changed nothing. A failed payment or a
spending limit persists across a reset, which is exactly what the record shows. Exhausted
minutes would not, and each failed run burns about two seconds, so the runs cannot be
consuming the quota themselves.

**The remedy is one action in GitHub → Settings → Billing & plans, by the account owner.**
No change to this repository can substitute for it. Making the repository public would
also lift the restriction, since public repositories get unrestricted Actions minutes —
recorded as a fact, not a recommendation, because it would publish the source and that is
not a decision code should make.

### What was reachable instead

C1's *literal* condition is blocked. Its *intent* — that the checks execute automatically
rather than when someone remembers — is reachable without a runner, and now holds:

- The enforcement layer runs in the suite (C2, C5, C6), so it is already independent of
  GitHub Actions entirely.
- `scripts/hooks/pre-push` runs the seven static checks on every push, on the developer's
  machine, with no runner and no minutes. Measured at **7 seconds**; verified to block by
  adding an undeclared verifier and watching the push fail with the ratchet's own message.
- `scripts/install-hooks.ps1` installs it, **opt-in**. Hooks change what `git push` does on
  someone's machine, and installing them as a side effect of an unrelated script is how the
  whole mechanism gets switched off. It also refuses to overwrite a pre-push hook it did
  not write.

The hook carries only the checks that need nothing to provision. The 24 MANUAL checks — the
PostgreSQL verifiers, the Kafka and object-store rehearsals, the OCI sandbox — belong to a
runner that can start services, and are declared with their cadences in
`oms/check_registry.py`. Putting them in the hook would make it slow enough to be bypassed,
which is the failure this goal is named after.

**C1 is closed as ACCEPTED, not met.** Decided 2026-08-13 by the repository owner: the
billing block stands and is not to be raised again. That is a reasonable call — the
condition asks for a green runner, the enforcement layer no longer depends on one, and the
remedy is a payment method rather than a commit.

Two consequences are stated once here so nobody has to rediscover them:

- The 24 MANUAL checks — the PostgreSQL verifiers, the Kafka and object-store rehearsals,
  the OCI sandbox — still have no automated home. They are declared with their cadences in
  `oms/check_registry.py`, and running them stays a deliberate act.
- `provenance.environment` will read `local` on every record. The distinction between "it
  passes on my machine" and "it passes in CI" exists in the schema and will not be
  exercised.

Neither is a defect to fix. They are the price of the decision, recorded so the next reader
sees a choice rather than an oversight.

## Explicit non-goals

Nor is the answer to move every check into the local suite. Eleven of them need a live
PostgreSQL, one needs an OCI sandbox, and the browser matrix needs Chromium; forcing those
into a laptop run would make the suite slow, flaky, and dishonest about what it covered.
The goal is that a check's execution history is *visible*, not that everything runs
everywhere.

## Why this and not something else

Three other directions were considered and are weaker:

- **The three MISSING pilot gates** — availability, RPO, RTO. Genuinely blocked on a
  deployed host held at a frozen head for seven days. Real work, but it is scheduling and
  infrastructure, and the harnesses are already built and tested.
- **The ten unprovenanced evidence files.** The ceiling has sat at 10 since it was set and
  has never fallen. Worth doing, and smaller than it looks.
- **Tier C** — external evaluators, SDK publication, compatibility-route retirement. Real
  scope, but advancing it while the enforcement layer is unexercised means adding claims to
  a system that cannot currently catch a broken one.

This goal is chosen because it invalidates the premise the others rest on. Every "the
ratchet held" in this repository's history is a statement someone made by hand. That may
well be true today — the four ratchets did hold when run on 2026-08-13 — but the project
has no way to notice the day it stops being true, and no record of when it last was.
