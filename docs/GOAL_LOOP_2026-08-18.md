# Goal — A loop that runs, not a loop that is remembered

Stated 2026-08-18. Follows [`GOAL_ITERATION_2026-08-17.md`](GOAL_ITERATION_2026-08-17.md),
which made the backlog readable. This is about making the loop *runnable*, which turned out
to be a different missing thing.

## The direction

The iteration goal answered *what is owed*. Forty-nine conditions carry a state, every check
runs where it says, every baseline is dated, and one command names the next step. That work
holds.

It left the other half untouched. **Knowing what to do next is not the same as being able to
do it**, and the evidence for that is this session: establishing that the tree was healthy
required an ad-hoc shell loop over 230 scripts, typed out by hand, **eight separate times**.

| | |
| --- | --- |
| Commands that verify the whole tree | **0** |
| Declared checks | 42 |
| Distinct cadences they declare | 7 |
| Checks whose cadence names no trigger (`per release candidate`, `on demand`) | **22 of 42** |

There is no `Makefile`, no `run_tests`, no `verify`. `check_registry.py` and
`iteration_state.py` both glob `oms/test_*.py` — to *count* the suite, never to run it.

## Finding 1 — the verification exists only as muscle memory

Everything needed is present and none of it composes:

| Step | Cost | How it is invoked today |
| --- | --- | --- |
| Python suite, 230 scripts | ~25 min | a `for` loop someone retypes |
| Browser suite | ~2 min | `measure_browser_evidence.py --build --run` |
| Suite-cost census | ~22 min | `measure_suite_cost.py`, then its audit |
| Fast audits | seconds | each invoked by name |

A person who wanted to know whether this repository is healthy would have to know all four,
in order, with the right flags. That knowledge lives in one head and in this document's
predecessors, which is precisely the failure the iteration goal was opened about — moved down
one level, from *what is owed* to *how it is checked*.

## Finding 2 — half the cadences name no trigger

`per release candidate` is declared by twenty checks and `on demand` by two. Neither names an
event that happens. There is no release-candidate ceremony in this repository and nothing
watches for one, so twenty-two of forty-two checks are, operationally, run when someone
remembers.

That is not necessarily wrong — a benchmark needing PostgreSQL and an object store should not
run on every push. What is wrong is that "per release candidate" reads like a schedule and
behaves like a hope.

## Finding 3 — evidence has a date now, and still no shelf life

`audit_iteration_state` dates every baseline and reports its age. Nothing says how old is too
old. `next_step` uses thirty days as a fallback, which was chosen for lack of anything better
and is stated nowhere the measurement itself can see.

A census measured against migration head `0042` is evidence about `0042`. When the head moves
it becomes a historical record, and today nothing but a human reading two fields notices.

## Conditions

- **K1 — One command verifies the tree.** **Met** — `oms/verify.py`, three tiers. Measured on
  the standard tier: 15 of 15 passed in 21.0 minutes, 14 static audits and 230 suite scripts,
  ending with the `Next:` line from the gate that knows. Tiered, because the costs differ by two
  orders of magnitude: seconds for the static audits, minutes for the browser, half an hour
  for the suite and the census. It reports one table — check, verdict, duration — and exits
  non-zero if anything failed. It is the thing a person types before pushing and the thing a
  scheduler would call.
- **K2 — Every measurement declares its shelf life.** **Open** — Each baseline records how
  long its evidence stays current, next to the date it already carries. The gate reports what
  is overdue and fails only on evidence that outlived a *stated* life, so the number is
  argued once rather than assumed every time.
- **K3 — A cadence names a trigger or admits it is manual.** **Open** — `per release
  candidate` is honest only if something defines a release candidate. Either that event
  exists and the checks hang off it, or the cadence is renamed to what it is, the way four
  checks were corrected from `every push` to `every suite run`.
- **K4 — The loop is written down as steps, not as habit.** **Met** —
  [`THE_LOOP.md`](THE_LOOP.md): status, take the named step, verify, record what it discharged,
  push. It states the ordering the `Next:` line uses, the three verification tiers and when to
  type each, and the two checks that report rather than gate. Written into the repository
  rather than reconstructed from commit messages.

## What this is not

Not CI. GitHub Actions is blocked on account billing and has been diagnosed as unfixable from
here; K1 is a command, and whether anything schedules it is K3's problem and not this
document's claim.

Not an argument that everything should run on every push. The opposite: the tiers exist so
that the cheap checks can run constantly and the twenty-minute ones can run deliberately,
with the difference stated rather than improvised.

And not a replacement for the iteration goal. That one answers *what to do next*; this one
answers *how to know it worked*. Both were needed and only one existed.
