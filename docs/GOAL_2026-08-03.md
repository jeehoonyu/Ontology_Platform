# OntologyOS Industrial Operational Intelligence Goal

Version 2, stated 2026-08-03 on `codex/builder-ux-production`.

This goal completes. [`GOAL_STANDING.md`](GOAL_STANDING.md) does not: it is the standing
discipline that keeps the claims below from outliving their proof once this document is
satisfied, and it is what the three defects recorded here were found by.

This goal supersedes the informal goal narrative used by
[`GOAL_ACCEPTANCE_2026-07-28.md`](GOAL_ACCEPTANCE_2026-07-28.md) and
[`GOAL_PROGRESS_2026-07-29.md`](GOAL_PROGRESS_2026-07-29.md). Those documents remain
authoritative as **evidence records**; this document is the **contract** they are
measured against. It does not claim Palantir source, API, or infrastructure
compatibility.

## Outcome

An operations team outside this project, starting from a fresh install and public
documentation alone, connects their own industrial data and reaches an approved,
evidence-linked decision report without writing code or editing raw JSON, and repeats
that run intact across an upgrade and a restore.

Everything below is a means to that outcome, not a substitute for it.

## Center of gravity

Every object, contract, action, and decision on that path is bound to an immutable
ontology revision. Every state change is append-only and carries actor, source,
transaction time, valid time, changed fields, ontology revision, and evidence
references. Breaking ontology changes are classified and acknowledged before they touch
an active schema, or they roll back atomically without drifting the live contract.

## In scope

1. The human-guided Connect-to-Report workflow, driven entirely through visible controls.
2. Normalized, project-scoped ontology contracts with temporal object change events.
3. Typed object and graph querying with filters, aggregation, temporal and spatial reads,
   masking, bounded expansion, and stable cursor pagination.
4. Content-addressed immutable dataset snapshots and a pluggable pipeline execution
   boundary with compiled plans, field lineage, and deterministic identities.
5. Governed provider-neutral AI that may retrieve context and propose actions but never
   unilaterally commits a governed mutation.
6. Collaborative visual builders with durable command receipts, revision fencing, and
   review/approval workflows.
7. Production observability, deployment, backup, restore, and failure recovery.
8. An additive, compatibility-preserving `/api/v1` surface.

## Explicitly out of scope

- Multi-region or internet-scale operation.
- Managed-service parity with any commercial platform.
- Palantir source or infrastructure compatibility.
- More than 50 concurrent users.
- Hosted model inference as a default execution path.

Work that advances an out-of-scope item does not advance this goal.

## Severity gate

Defect severity is distinct from the requirement priority column in
[`VALIDATION_MATRIX.md`](../foundry-docs/VALIDATION_MATRIX.md). The two must not be
reported as one number.

- **P0 defect** — blocks the outcome path, or loses or corrupts committed data,
  evidence, or tenant isolation.
- **P1 defect** — degrades the outcome path or its governance guarantees, with a
  documented workaround.
- **P2 defect** — everything else.

No tier is claimed while an unresolved P0 or P1 defect is open against its scope. Any
downgrade from P0 or P1 to P2 is recorded in that tier's acceptance record with owner,
date, and rationale. Environmental blockers outside the product are recorded as
conditions with a named owner, not silently absorbed.

## Non-completion rule

No tier is marked complete while any of its conditions lacks objective evidence. Partial
progress is reported as a measurement, never as a status word.

### GOAL2-001

`db.commit()` expires the artifact ORM row, so `_artifact_dict` re-selected the artifact
head when building the response. A writer that committed first, then lost the race to
finish its response, was handed the competing writer's `current_revision`,
`lock_version`, and `state`.

Committed data was never corrupted: every revision row remained unique and correctly
numbered, and each `ArtifactCommandReceipt` recorded the correct revision. The defect was
confined to what the caller was told. It is P1 rather than P0 because it degrades the
collaborative-authoring guarantee without losing committed data or evidence: a client
that adopts the returned `lock_version` as its next base can skip its own revision and
silently adopt a peer's state without any conflict signal.

Reproduced at 6 anomalies in 150 concurrent rounds on SQLite. The PostgreSQL path shared
the same response construction and the same exposure.

Fixed by pinning the response to the revision the request allocated. `_artifact_dict`
accepts optional `pinned_revision` and `pinned_lock_version` arguments, and the three
handlers that allocate a revision capture those values before committing:
`update_artifact`, `apply_artifact_commands`, and `apply_collaborative_commands`. All
other callers are unchanged and still describe the artifact head.

Verified at 0 anomalies in 300 rounds and 600 requests after the fix.

`oms/test_artifact_collaboration.py` previously exercised this race for a single round
and so detected the defect only occasionally, which is why it surfaced as an
intermittent failure rather than a reproducible one. It now repeats the race for 120
rounds on a dedicated `collaborative_race` artifact, and additionally asserts that each
response agrees with its own command receipt. The dedicated artifact keeps the added
revisions from perturbing the event-cursor and receipt-count expectations in the rest of
the test. With the fix reverted the strengthened test failed 3 of 3 runs; with the fix in
place it passed 3 of 3, at a cost of about 7 seconds.

### GOAL2-002

`test_docs_conformance.py` dispatched an ontology object-change event chosen with
`next(...)` over `/api/v1/outbox/events`, then asserted that a binding filtered to
`object_type_ids: ["asset"]` routed at least one event.

That listing is ordered `created_at DESC, id`. The four object-change events it scans —
one `work_order` and three `asset` — are enqueued inside the same second, so the ordering
tie breaks on a random identifier. When the `work_order` event sorted first the test
dispatched it, the asset-filtered binding matched nothing, and the run failed with
`scanned: 1, matched: 0`.

Measured at 2 failures in 8 runs before the fix, which is why it passed standalone and
failed in both full-suite runs. No product behavior is involved: the routing matcher
correctly declined an event whose object type the binding excludes. Severity is P2
because it degrades the verification harness rather than the outcome path, but it blocks
Tier A, which requires the suite to pass in one sequential run.

Fixed by selecting the object-change event whose payload object type matches the binding
the test creates, rather than trusting list order. Verified at 12 passes in 12 runs.

### GOAL2-003

Tier A requires the migration upgrade **and downgrade** chain to pass. The upgrade chain
was already verified on both dialects, but a full downgrade to base had not been
exercised. On SQLite it failed at `0018_project_scoped_ai_evals` with
`no such column: project_id`.

Six migrations added a column, created an index on it, and then dropped the column in
`downgrade()` without dropping the index first: `0007_project_ingestion_runtime`,
`0014_import_project_scope`, `0015_pipeline_project_scope`,
`0016_workshop_project_scope`, `0017_governed_automation_project_scope`, and
`0018_project_scoped_ai_evals`. Migrations `0019` onward, plus `0004`, `0011`, `0030`,
and `0033`, already handled it correctly, so the fix restores an existing convention
rather than introducing one.

The defect is dialect-specific, which is why the PostgreSQL-only CI job never caught it.
PostgreSQL removes dependent indexes by cascade on `DROP COLUMN`. SQLite either rebuilds
the table and recreates the reflected index against a column that no longer exists, or
leaves the stale index behind and rejects the table on next access — the two distinct
error messages observed while walking the chain down.

Severity is P1: SQLite is the default local database, so an operator who upgraded and
needed to roll back could not, which degrades the recovery guarantee. It is not P0
because no committed data is lost and a documented workaround exists — restore from
backup per [`RECOVERY.md`](RECOVERY.md).

Fixed by dropping the `ix_{table}_project_id` index before the column in all six, using
the same guarded pattern `0019` already uses. Verified by a full `upgrade head ->
downgrade base -> upgrade head` round-trip on both dialects, each ending at
`0037_cross_stream_joins`, with PostgreSQL returning to 272 tables.

### GOAL2-004

`verify_collaboration_scale_postgres.py` drives 20 concurrent editors and judges the
acknowledgement p95 against a 250 ms threshold. A p95 over 20 samples is the 19th
value, so the gate is decided by one observation and moves with a single slow request.

Three consecutive runs at head `0037` on one host measured **241.605 ms, 253.002 ms, and
219.812 ms** — a 33 ms spread straddling the threshold. Correctness held in all three:
20 unique contiguous revisions, zero lost updates, every editor acknowledged. Only the
latency threshold moved.

The earlier record shows the same instability across hosts: 206.458 ms and 224.866 ms on
2026-07-29, 241.605 ms earlier on 2026-08-03. The trend is not evidence of regression so
much as evidence that the estimator is too noisy to support a hard threshold.

Recorded as P2 because it degrades the verification apparatus rather than the product,
and no user-facing behavior is implicated. It nonetheless blocks the Tier B collaboration
gate, which is recorded FAIL at the worst of the three observations rather than the best.

### GOAL2-005

`0001_runtime_baseline` upgrades by calling `Base.metadata.create_all(checkfirst=True)`.
The baseline therefore materializes whatever the ORM defines at the moment it runs, rather
than a fixed schema. Measured on 2026-08-03: **215 of 271 tables** are created by no
explicit migration and arrive only that way.

A database created today receives all 271. A database that ran the baseline before a model
was added received the tables that existed then, and no later migration supplies the rest.
Both report head `0037_cross_stream_joins`.

Two consequences, the second easy to miss:

1. **Upgrade.** An existing pilot can silently lack tables that code, routes, and tests all
   assume. The interface tables are a live example — real, routed, and tested, but present
   only in databases created after those models landed.
2. **Evidence provenance.** `migration_head` is the staleness key in every Tier B evidence
   file and in `audit_evidence_corpus.py`. If head does not determine schema, two evidence
   files can both read CURRENT at the same head while describing different systems. The
   provenance model built on 2026-08-03 is weaker than it appears, and this defect is the
   reason.

P1 rather than P0: no committed data is lost, and a documented workaround exists — create
fresh and restore, per [`RECOVERY.md`](RECOVERY.md). It is not P2 because it degrades the
upgrade guarantee and quietly weakens the evidence rule the goal depends on.

**Fixed 2026-08-04** by `0038_explicit_schema_baseline`, which states all 271 tables and
849 indexes explicitly. Every statement is guarded, so it is a no-op on a database that
`0001` already populated and a catch-up on one that predates these models.

Verified against a real PostgreSQL rather than by inspection. A database stamped at `0037`
holding **zero tables** — the worst case an old deployment can present — upgraded to **272
tables** at `0038`, with the interface tables among them. A fresh install still reaches the
same 272, the upgrade is idempotent on a second run, and a full `downgrade base ->
upgrade head` round-trip passes on both SQLite and PostgreSQL. Baseline-only tables fell
from 215 to **0**, and `oms/test_schema_identity.py` now holds the ceiling there.

This does not retrofit determinism onto `0001`; it converges every deployment at `0038`
and the ratchet prevents new tables from reopening the gap. `downgrade` is deliberately
empty: this revision only adds tables a deployment was missing, and dropping them would
destroy data that `0001` created everywhere else.

Two consequences worth recording:

- Advancing the head **invalidated the one Tier B gate that was passing**. The chaos
  evidence was earned at `0037` and now reads STALE, so Tier B fell from 1 of 10 back to
  0 of 10. That is the non-completion rule working rather than failing, and the gate has
  to be re-run rather than re-dated.
- The fix exposed a silent flaw in the instrument built to police it. `current_head()`
  matched `revision = "..."` but Alembic autogenerate emits `revision: str = "..."`, so the
  auditor reported the old head and would have kept reporting evidence as CURRENT
  indefinitely. The regex now accepts both forms, and the migration follows the repository
  convention as well.
